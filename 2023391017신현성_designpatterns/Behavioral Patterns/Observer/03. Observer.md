# Observer Pattern

> **카테고리:** Behavioral Patterns (행동 패턴)  
> **학습 순서:** 3/22

---

### 1. 한 줄 요약

**한 객체의 변화가 생겼을 때, 그 객체를 지켜보는 여러 객체에게 자동으로 알려주는 패턴이다.**

### 2. 사용하는 이유

Player의 HP가 바뀔 때 UI, 사운드, 화면 효과 등이 모두 갱신되어야 한다고 하자. Player가 모든 시스템을 직접 호출하면 서로 강하게 연결된다. Observer를 사용하면 Player는 구독자들에게 변화가 생겼다고 알리기만 하면 된다.

### 3. 핵심 구조

- **Subject / Publisher**: 변화를 알리는 객체
- **Observer / Subscriber**: 변화를 통보받는 객체
- **구독 목록**: 현재 알림을 받을 Observer들의 목록

### 4. 동작 과정

1. Observer가 Subject에 자신을 등록한다.
2. Subject의 값이나 상태가 바뀐다.
3. Subject가 등록된 Observer들에게 알림을 보낸다.
4. 각 Observer가 자신의 일을 처리한다.

### 5. 게임 개발 예시

Player의 HP가 감소하면 HPBar UI, 피격 사운드, 화면 붉은 효과가 동시에 반응하도록 만들 수 있다.

### 6. 간단한 Lua 예제

```lua
local Player = { hp = 100, observers = {} }

function Player:addObserver(observer)
    table.insert(self.observers, observer)
end

function Player:setHP(value)
    self.hp = value

    -- 등록된 모든 Observer에게 알림
    for _, observer in ipairs(self.observers) do
        observer:update(self.hp)
    end
end

local HPBar = {}
function HPBar:update(hp)
    print("HP UI 갱신:", hp)
end

Player:addObserver(HPBar)
Player:setHP(70)
```

### 7. 장점

- Publisher와 Subscriber의 결합도를 낮출 수 있다.
- 여러 객체가 하나의 변화에 쉽게 반응할 수 있다.
- 구독자를 실행 중에 추가하거나 제거하기 쉽다.

### 8. 단점

- 구독자가 많아지면 호출 흐름을 추적하기 어렵다.
- 알림 순서에 의존하면 문제가 생길 수 있다.
- 구독 해제를 제대로 하지 않으면 불필요한 참조가 남을 수 있다.

### 9. 핵심 키워드

`구독`, `알림`, `이벤트`, `상태 변화 통지`, `Publisher/Subscriber`

### 10. 헷갈리기 쉬운 패턴

#### Observer vs Mediator

- **Observer**: 한 객체의 변화를 여러 구독자에게 알리는 구조다.
- **Mediator**: 여러 객체가 서로 직접 통신하지 않고 중재자 하나를 통해 통신한다.

> HP 변경을 UI에게 알려준다 → **Observer**  
> 여러 UI 창의 상호작용을 UIManager가 중재한다 → **Mediator**
