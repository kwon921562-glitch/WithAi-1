# 디자인 패턴 22개 쉬운 요약

퀴즈에서 상황을 보고 바로 패턴을 떠올릴 수 있도록  
**핵심 뜻 + 쉬운 예시 + 구분 포인트**로 정리했습니다.

| 패턴 | 쉽게 말하면 | 게임 예시 | 기억할 키워드 |
|---|---|---|---|
| **Strategy** | 여러 행동 중 하나를 골라서 바꿔 쓰는 패턴 | 검 공격 / 활 공격 / 마법 공격을 교체 | **행동 교체** |
| **State** | 현재 상태에 따라 행동이 달라지는 패턴 | Idle / Run / Attack / Dead 상태 | **상태에 따른 행동 변화** |
| **Observer** | 한 객체가 바뀌면 다른 객체들에게 알려주는 패턴 | HP가 줄면 체력 UI가 자동 갱신 | **변화 알림** |
| **Factory Method** | 어떤 객체를 만들지는 하위 클래스나 별도 생성 로직에 맡기는 패턴 | GoblinFactory가 Goblin 생성 | **생성 위임** |
| **Adapter** | 서로 맞지 않는 인터페이스를 연결해주는 패턴 | 외부 라이브러리를 기존 게임 코드에 맞게 연결 | **형식 변환 / 연결** |
| **Facade** | 복잡한 여러 기능을 하나의 간단한 사용법으로 묶는 패턴 | 게임 시작 시 사운드, UI, 맵 로딩을 한 번에 처리 | **복잡함 단순화** |
| **Composite** | 여러 객체를 트리 구조로 묶어 하나처럼 다루는 패턴 | UI 패널 안에 버튼과 텍스트를 계층 구조로 관리 | **트리 구조** |
| **Decorator** | 기존 객체를 수정하지 않고 기능을 덧붙이는 패턴 | 기본 검에 불 속성, 독 속성 추가 | **기능 추가** |
| **Memento** | 현재 상태를 저장해두었다가 다시 복구하는 패턴 | 체크포인트 저장 후 이전 상태로 복원 | **저장 / 복원** |
| **Prototype** | 기존 객체를 복사해서 새 객체를 만드는 패턴 | 기본 몬스터를 복제해 여러 마리 생성 | **복제 생성** |
| **Mediator** | 객체들이 직접 서로 연락하지 않고 중간 관리자에게 맡기는 패턴 | 여러 UI 창의 상호작용을 UIManager가 관리 | **중재자** |
| **Proxy** | 실제 객체 대신 대리 객체가 접근을 대신 관리하는 패턴 | 필요한 순간에만 무거운 리소스를 실제로 불러옴 | **대리 / 접근 제어** |
| **Abstract Factory** | 관련된 객체들을 하나의 세트로 묶어서 생성하는 패턴 | 불 지역용 적 + 무기 + 아이템 세트를 생성 | **제품군 생성** |
| **Flyweight** | 여러 객체가 공통 데이터를 공유해 메모리를 아끼는 패턴 | 수천 그루의 나무가 같은 텍스처 데이터 공유 | **공유 / 메모리 절약** |
| **Template Method** | 전체 작업 순서는 고정하고 일부 단계만 바꾸는 패턴 | 모든 적 AI의 기본 흐름은 같고 공격 방식만 다름 | **알고리즘 틀** |
| **Singleton** | 프로그램 전체에서 객체 하나만 사용하게 하는 패턴 | GameManager 하나만 존재 | **하나만 존재** |
| **Builder** | 복잡한 객체를 여러 단계로 나눠서 만드는 패턴 | 캐릭터의 직업, 무기, 방어구를 단계별 설정 | **단계별 생성** |
| **Iterator** | 내부 구조를 몰라도 여러 요소를 하나씩 순서대로 보는 패턴 | 인벤토리 아이템을 처음부터 끝까지 순회 | **순회** |
| **Visitor** | 기존 객체 구조를 바꾸지 않고 새로운 처리를 추가하는 패턴 | 여러 몬스터에게 통계 계산 기능을 추가 | **새 기능 방문** |
| **Bridge** | 기능과 실제 구현을 따로 분리해서 각각 변경할 수 있게 하는 패턴 | 무기 종류와 공격 이펙트를 독립적으로 변경 | **추상화 / 구현 분리** |
| **Chain of Responsibility** | 요청을 여러 처리자에게 차례대로 넘기는 패턴 | 입력을 UI → Player → GameManager 순서로 처리 | **요청 전달** |
| **Command** | 행동이나 요청 자체를 하나의 객체로 만드는 패턴 | 이동, 공격 명령을 저장해 Undo나 리플레이에 사용 | **명령 객체화** |

# 퀴즈에서 바로 떠올리는 핵심 문장

- **행동이나 알고리즘을 바꿔 끼운다** → `Strategy`
- **현재 상태에 따라 행동이 달라진다** → `State`
- **변화가 생기면 다른 객체에게 알려준다** → `Observer`
- **객체 생성을 다른 쪽에 맡긴다** → `Factory Method`
- **서로 안 맞는 인터페이스를 연결한다** → `Adapter`
- **복잡한 시스템을 간단한 창구 하나로 사용한다** → `Facade`
- **객체를 트리 구조로 묶어서 다룬다** → `Composite`
- **기존 객체에 기능을 덧붙인다** → `Decorator`
- **상태를 저장했다가 이전 상태로 되돌린다** → `Memento`
- **기존 객체를 복사해서 새 객체를 만든다** → `Prototype`
- **객체들 사이의 소통을 중간 객체가 관리한다** → `Mediator`
- **실제 객체 대신 대리 객체를 사용한다** → `Proxy`
- **관련된 객체들을 한 세트로 생성한다** → `Abstract Factory`
- **공통 데이터를 공유해서 메모리를 아낀다** → `Flyweight`
- **전체 순서는 고정하고 일부 단계만 바꾼다** → `Template Method`
- **객체 하나만 존재하게 한다** → `Singleton`
- **복잡한 객체를 단계별로 만든다** → `Builder`
- **여러 데이터를 순서대로 하나씩 본다** → `Iterator`
- **기존 구조는 유지하고 새로운 기능을 추가한다** → `Visitor`
- **기능과 구현을 따로 분리한다** → `Bridge`
- **요청을 여러 처리자에게 차례대로 넘긴다** → `Chain of Responsibility`
- **요청이나 행동 자체를 객체로 만든다** → `Command`

# 헷갈리기 쉬운 패턴 초간단 비교

- **Strategy vs State**
  - Strategy: 내가 사용할 **행동을 선택**
  - State: 현재 **상태 때문에 행동이 변경**

- **Factory Method vs Abstract Factory**
  - Factory Method: **한 종류의 객체 생성 방식**에 초점
  - Abstract Factory: **관련 객체 여러 개를 한 세트로 생성**

- **Adapter vs Facade**
  - Adapter: **서로 안 맞는 것을 맞춰줌**
  - Facade: **복잡한 것을 간단하게 보여줌**

- **Decorator vs Proxy**
  - Decorator: **기능을 추가**
  - Proxy: **접근을 대신 관리**

- **Template Method vs Strategy**
  - Template Method: **전체 흐름은 고정**, 일부만 변경
  - Strategy: **행동 전체를 교체**

- **Observer vs Mediator**
  - Observer: 변경 사실을 **여러 객체에게 알림**
  - Mediator: 여러 객체 사이의 **대화를 중간에서 관리**

- **Command vs Chain of Responsibility**
  - Command: **요청 자체를 객체로 만듦**
  - Chain of Responsibility: **요청을 여러 처리자에게 넘김**
